# AI Email Support Agent — Product & Architecture Design

> Status: **APPROVED** by Robert, 2026-09-07 (brainstormed in plan mode). This spec is normative: when an implementation plan and this spec disagree, the spec wins and the discrepancy must be flagged. Provenance: a 6-agent read-only map of doge-buddy + completeness critic; three-lens architecture designs → synthesis → 45-finding adversarial review (all blockers and majors applied); a focused LLM-adapter design; verified external facts (Better Auth Expo/organization plugins, Gmail restricted scopes + CASA, Microsoft Graph subscriptions, Expo Router web, Voyage embeddings). Next: Phase 0 implementation plan in `docs/superpowers/plans/`.

## Context

**What prompted this.** `~/Desktop/code/ClosingBrackets/doge-buddy` contains a production-proven, single-business email support agent (Phase 6A/6B + guidance/redraft + contact form): Gmail ingest → Haiku triage → Claude drafting agent with read-only tools → plain-code validator → owner approval → threaded send. It works for one store, one mailbox, one owner on Telegram. Robert wants to turn that concept into a **multi-tenant SaaS**: any business signs up, connects its support mailbox(es), gives the agent knowledge, flips it on, and the agent answers customer email.

**Intended outcome.** A product where a business can go from signup to "the agent is answering my support inbox" in under 15 minutes, with a review loop that builds trust and a learning loop that makes the agent need less review over time. Built in this repo (`ai-email-support-agent`, currently empty) with UX as the top priority and best practices, maintainability, readability, scalability and performance as hard requirements.

**What doge-buddy teaches us (carried forward as principles).**
1. The agent must be architecturally unable to do harm: it drafts, plain code validates, a policy decides whether it sends. No money/send tools inside the model loop.
2. Customer email is untrusted input; owner guidance is trusted input; a deterministic tripwire (legal, injury, chargeback…) escalates regardless of what the model says.
3. Idempotency everywhere: message dedupe on provider ids, guarded state transitions, send-recovery markers, staleness guards (a draft never sends over a newer customer message).
4. The owner's real stance and the written policy WILL disagree; a live-editable guidance layer and a reject-with-reason re-draft loop close that gap without a deploy.
5. Deliverability and threading are product features: `In-Reply-To`/`References`, send from the business's real address, DMARC-aware.

## LLM provider adapter (`packages/llm`)

**Shape.** A small `LlmProvider` interface with two v1 adapters over native SDKs: `adapters/anthropic` (`@anthropic-ai/sdk`: `messages.parse` + `zodOutputFormat`, `beta.messages.toolRunner`, `cache_control`, adaptive thinking + `output_config.effort`) and `adapters/openai-compatible` (`openai` SDK with `baseURL` + presets for OpenAI, DeepSeek, Groq, Together, OpenRouter, Ollama, vLLM, LM Studio). Google Gemini is a documented seam (`adapters/google`, `@google/genai`) with Gemini's OpenAI-compatible endpoint as the stopgap. **Not** the Vercel AI SDK: Anthropic-specific features (caching, effort, structured outputs, refusal fallbacks) arrive there late or only via escape hatches, its yearly breaking majors cost more than two adapters, and its wrapped errors lose the provider `type` we need for retry decisions. The interface is kept AI-SDK-shaped so a bridge adapter can be added if providers grow past four.

```ts
type Stability = 'static' | 'agent' | 'volatile'          // maps to caching breakpoints
interface SystemBlock { id: string; text: string; stability: Stability }
interface ChatRequest<T> { model; system: SystemBlock[]; messages; output?: { name; schema: ZodType<T> };
  tools?: ToolDef[]; maxToolRounds?; effort?: 'low'|'medium'|'high'; maxOutputTokens; signal;
  meta: { orgId; agentId?; runId?; role: 'triage'|'draft'|'guidance_suggest'|'probe'; idempotencyKey } }
interface ChatResult<T> { text; parsed: T | null; parseStrategy: 'native'|'json_mode'|'repair'|'extract'|'none';
  toolTrace; usage: { inputTokens; outputTokens; cacheReadTokens; cacheWriteTokens; reasoningTokens?; apiCalls };
  finish: 'stop'|'length'|'tool_limit'|'refusal'|'unknown'; provider; model; latencyMs; providerRequestId? }
interface LlmProvider { kind; capabilities(model): Capabilities; chat<T>(req): Promise<ChatResult<T>>;
  stream?<T>(req): AsyncIterable<StreamEvent> /* sandbox only */; probe(model?): Promise<ProbeResult> }
class LlmError { code: 'auth'|'rate_limit'|'context_too_long'|'content_filtered'|'transient'|'permanent'; retryable; retryAfterMs? }
```
`createProvider(config, credential)` wraps the raw adapter as `withStructuredLadder → withLimiter → withMetering`.

**Capabilities are probed, not assumed.** Presets per model (`adapters/*/models.ts`) are overridden by the stored probe result from "Test connection" (models list, one tiny chat, a 2-field structured-output probe, an `echo` tool probe) and a 6-hourly cheap re-probe (`degraded` after two failures, `dead` on auth failure → UI badge + owner notification; a dead credential routes tickets to Review with "AI provider unavailable" rather than failing).

| Provider | Structured output | Tools | Caching | Notes |
|---|---|---|---|---|
| Anthropic opus-5 / sonnet-5 | native | yes | explicit `cache_control` (min 512 / 1024 tokens) | adaptive thinking; `effort` |
| Anthropic haiku-4-5 | native | yes | explicit but min 4,096 tokens (triage prompts won't cache) | no `effort` |
| OpenAI GPT | native (`json_schema` strict) | yes | automatic ≥1,024-token prefix | `reasoning_effort` on reasoning models |
| DeepSeek | `json_object` only | flaky | automatic | prompt must mention JSON |
| Generic OpenAI-compatible | probe-determined | probe-determined | none | Groq/Together/OpenRouter |
| Ollama / vLLM / LM Studio | `json_schema` accepted but unreliable <~30B → treated as `json_mode` unless probe passes | default off | none | confidence capped (see risks) |

**Fallback ladder for the draft schema:** native → JSON-mode + zod parse → one low-effort repair call (no tools, 1K tokens) → balanced-brace extraction → `permanent/output_invalid` → ticket to Review. **Pre-retrieval is the primary path for every provider** (retrieval scores feed the confidence formula anyway; removes 2 of 3 API calls per draft; provider-agnostic; testable). Triage emits `questions[]`; each is embedded and searched, results merged. Tool calling is an optional second pass only when the provider supports it and the agent has integrations enabled — off in v1.

**Prompt blocks → caching.** Assembly yields ordered blocks: platform hard rules (`static`) → workspace profile, persona, guidance (`agent`) → retrieved chunks + resolved cases (`volatile`); the thread goes in `messages`; tools sorted by name. Anthropic: breakpoint 1 on the last static block (`ttl: '1h'`, shared by all tenants), breakpoint 2 on the last agent block (5 min), skipped when the prefix is under the model's minimum. OpenAI-compatible: same order concatenated into one system message so automatic caching benefits. A recorded-fixture test asserts `cacheReadTokens > 0` on the second identical request; a `cache_read / (input + cache_read)` metric per model catches regressions. Managed mode may set Anthropic's server-side refusal fallback so a refusal is retried before surfacing `content_filtered`.

**Config + metering tables** (all org-scoped, RLS): `llm_credentials` (provider, label, `key_ciphertext`/`key_nonce`/`data_key_version`, `key_fingerprint` display-only, `base_url`, `extra_headers_ciphertext`, `transport 'direct'|'bridge'`, `egress_allowlist[]`, `health_status`, `last_probe jsonb`), `org_data_keys` (per-org AES-256-GCM data key wrapped by KMS, `MASTER_KEY` in dev; rotation = new version + lazy re-wrap), `agent_model_config` (agent or workspace default × role → `mode 'managed'|'byok'`, `credential_id`, provider, model, effort, `fallback_to_managed`, `model_generation` — bumping it resets graduation streaks), `model_pricing` (platform, versioned by `effective_from`, pattern match, unknown BYOK model → `cost_unknown`), `llm_calls` (append-only per call: tokens by class, `pricing_id`, `cost_usd`, latency, finish, parse strategy, error code; idempotency key unique; monthly partitions later), `usage_counters` (per org per UTC day: `ai_conversations_handled`, `llm_calls`, `llm_cost_usd`, tokens). `withMetering` writes `llm_calls` + upserts `usage_counters` after every call in its own short transaction and never throws into the run; `ai_conversations_handled` is incremented by the runtime only when a draft is produced. Billing reads `ai_conversations_handled` for managed overage (Stripe metered price) and `llm_cost_usd` for the daily spend circuit breaker and margin dashboards.

**Security.** `Secret` branded type (serializes as `[redacted]`), decrypted only inside `createProvider`; error normalizer scrubs `sk-`, `Bearer `, and key tails; pino redact paths for auth headers. SSRF: https only, hostname required, all A/AAAA resolved and rejected for loopback / RFC1918 / link-local incl. `169.254.169.254` / CGNAT / multicast / `fc00::/7`; `pinnedFetch` (undici Agent with lookup override pinning the vetted IP, `redirect: 'manual'`) injected into both SDKs so DNS rebinding cannot swap targets; optional per-org egress allowlist. Limiters keyed `managed:${provider}:${model}` (shared, sized to our tier) or `byok:${orgId}:${credentialId}` (a stalled BYOK tenant never consumes managed capacity). Job policy per error code: auth → credential dead + notify + Review; rate_limit → `startAfter = retryAfterMs`, max 5; context_too_long → halve retrieval, retry once; content_filtered → Review; transient → 3 backoff retries; permanent → Review + alert.

**Default models** (seed; verify IDs against `/models` at implementation): Anthropic triage `claude-haiku-4-5` / draft `claude-opus-5` (`effort: high`, `claude-sonnet-5` as cost tier); OpenAI `gpt-5-mini` / `gpt-5`; DeepSeek `deepseek-chat`; Groq `llama-3.1-8b-instant` / `llama-3.3-70b-versatile`; OpenRouter `anthropic/claude-haiku-4.5` / `anthropic/claude-opus-5`; Ollama `qwen3:8b` / `qwen3:32b`.

**Embeddings** stay platform-managed (Voyage) via a separate `Embedder` interface; `knowledge_chunks` and `resolved_cases` carry `embedding_model` + `embedding_version`, so provider-chosen embeddings later = an `embed` role + a `ReembedWorkspace` job that cuts over atomically (pgvector columns are dimension-typed; fix 1024).

**Local on-prem (stretch).** Cheapest credible path: a customer-run `bridge` binary next to Ollama that opens an outbound WebSocket to our API with a pairing token; the OpenAI-compatible adapter routes through it via the injected `fetch`. Interim: Cloudflare Tunnel + Access service token stored in `extra_headers`. v1 keeps this possible by (a) `fetch` injection, (b) the `transport` column, (c) plain JSON request/response with no SDK streaming assumptions in the draft path.

**Package layout.** `packages/llm/src/{core/{types,errors,prompt,structured,tools,limiter,registry,probe}, adapters/anthropic/{index,map-request,map-errors,models}, adapters/openai-compatible/{index,presets,map-errors,structured-mode}, adapters/google/README, pricing/{seed,cost,types}, ssrf/{validate-url,pinned-fetch,ranges}, crypto/{envelope,secret}, metering/{types,noop-sink}, testing/{fake-provider,contract-suite,recorder,fixtures/}}`. Tests: `FakeProvider` with scripted responses + capability overrides (exercises every ladder step); `runProviderContract(makeProvider)` that both adapters pass at HTTP level via undici `MockAgent`; `LLM_RECORD=1` scrubbed fixtures replayed in CI; `LLM_LIVE=anthropic,openai,ollama` live runs including the cache-read assertion. `packages/llm` has no DB dependency; the `MeterSink` lives in `packages/db`.

**Risks:** provider drift (presets with quirk flags, probe-driven capabilities, contract suite, pinned SDKs); quality variance skewing confidence (self-assessment is a minority weight; per-`(provider, model)` calibration from edit rates; local/small models capped at 0.6 → always Review unless the owner overrides); BYOK rate limits stalling runs (per-org limiter, `retryAfter` into pg-boss, health badge, opt-in billable `fallback_to_managed`); some models reject structured output + tools together (two-phase: tool loop, then schema-only final call).

## Pricing economics (why an allowance)

Per handled conversation, model cost with prompt caching (stable prefix cached, retrieval + thread uncached):

| Step | Model | Approx. tokens | Approx. cost |
|---|---|---|---|
| Triage/classification | claude-haiku-4-5 | 2K in / 0.1K out | $0.003 |
| Draft (2 tool round-trips) | claude-opus-5 | ~8K in (≈2K cached) / ~1.5K out incl. thinking | $0.07–0.09 |
| Embeddings (question + case lookup) | voyage-4-lite | ~1K | <$0.001 |
| Re-draft / follow-up share | — | ×1.3 average | — |
| **Total** | | | **≈ $0.10–0.15 / conversation** (≈ $0.04–0.06 if a plan tier uses claude-sonnet-5) |

At $49.99/domain the break-even is ≈ 350 conversations/month on model cost alone, before infrastructure and support. Decision (with Robert's profit rule): **$49.99 includes 3 agents + 300 AI-handled conversations per domain per month under Managed AI; above that, automatic overage at $0.12 per conversation (Stripe metered price) or a "blocked" mode; escalated-without-draft mail is never counted; BYOK customers pay the subscription only.** Prepaid packs and a "Business" tier can come later without changing the metering model. Managed AI also carries a per-org daily LLM spend cap (trial $3, standard $60) and a trial budget so no single workspace can spend the platform's money.

## Agents & personas (added 2026-09-07)

- **Agent** = `{ address, mailbox connection, reply-from address, persona, model config, autonomy policy, signature }`. Up to 3 per domain. Several agents may share one OAuth connection when the addresses are aliases/groups delivered to the same mailbox; otherwise each address's mailbox is connected separately. An address that is not the connection's own is verified by an inbound one-time code (never by an outbound test send); if it cannot send as itself, replies go out from the connection address (`reply_from_address`) until Send-as is configured. Inbound routing: a message is handled by the agent whose address appears in To/Cc/Delivered-To (first match by priority order the owner sets); mail to the mailbox that matches no agent is never fetched in full. Agents are never pre-created — the owner ticks each address explicitly, and adding an address to a mailbox someone else connected needs that person's one-tap consent.
- **Persona presets** ship with tone, goals, boundaries, default autonomy and a signature template:
  - *Support* — helpful, concise, resolves; default Review → Autopilot by category.
  - *Sales* — warm, consultative, always offers a next step (call/booking link from the profile), never invents pricing or discounts, hands negotiation and quotes above a configurable amount to a human; default Review.
  - *Concierge / Informative* — neutral, thorough, cites sources; never sells; highest auto-graduation potential.
  - *Billing* — precise, cautious, never states amounts it cannot ground, escalates disputes; default Review.
- **Custom persona**: a bounded text box (≤ 4,000 chars) "Who is this agent, how should it sound, what should it always/never do", rendered as a trusted prompt layer *below* the platform hard rules and *above* the knowledge/thread. It can shape tone and priorities; it cannot enable promises, links, contact channels or topics the guardrails block. Each agent has its own sandbox ("Try it") and its own confidence/graduation stats.
- **Prompt layering (final):** platform hard rules (immutable) → workspace profile → **agent persona** → knowledge (retrieved chunks + resolved cases) → operating guidance (workspace-wide + per-agent additions) → thread (untrusted). Persona and guidance are cached as part of the stable prefix per agent.

**Replace.**

**Cross-cutting rules for the new codebase (from the completeness critic's pass over the reference).**
- **One tenant seam, chosen up front.** The reference redeclares its `Db` type alias 50 times, so tenancy cannot be retrofitted at the handle. New rule: every table carries `org_id`; all data access goes through a scoped `TenantDb` (constructed from `orgId`, adds the predicate by construction) **and** Postgres row-level security with `SET LOCAL app.org_id` on every transaction as a second net. Raw handle access is allowed only in platform code (migrations, metering rollups, crons that fan out per org).
- **Typed job contracts.** The reference's `enqueue(name, data)` is untyped; adding `tenantId` to payloads has no compile-time enforcement. New rule: a job registry `defineJob(name, zodSchema, handler)` where every payload schema includes `orgId`, and `singletonKey` is always `${orgId}:${entityId}`.
- **Split the overloaded audit table.** In the reference `audit_log` is simultaneously the audit trail, alert store, rate-limit counter and metrics source, with no time index. New rule: `audit_log` (append-only trail with a real actor), `usage_counters` (per-org, per-day metering the caps and billing read), alerts to logs/error tracker, analytics from proper tables.
- **Actor identity from day one.** The reference writes `actor: 'system' | 'owner'` at 82 call sites. New rule: `actor` is `user:<id>` / `agent:<run_id>` / `system:<job>`; approvals record the user.
- **Staleness watermark is a column, not payload.** The reference buries `threadSnapshotAt` inside a zod payload in a shared package; a reshaped payload would silently disable the stale-send guard. New rule: `drafts.thread_snapshot_at` is a real column and the send path refuses a NULL.
- **Invariants become checks, not comments.** Coupled constants (redraft max vs per-ticket daily cap, claim-stale ms vs queue expiry, failure-escalate threshold) are asserted at startup and tested, because they become per-plan configuration.
- **Never trust a caller-supplied IP** (the reference's contact endpoint prefers the client-supplied `ip` for Turnstile). The API reads the proxy header chain it controls.
- **PII posture.** Bodies, transcripts and tool results are PII at rest: encrypt OAuth tokens (envelope encryption with a KMS/`MASTER_KEY`-derived data key, rotation supported), redact bodies from logs, define retention (default 180 days for message bodies and agent traces, configurable per plan) and an org-delete path that cascades.
- **Doge-buddy stays untouched.** It is a live business with active commerce churn; the SaaS is a clean port into this repo (≈4,600 lines of support + Gmail code travel with edits; ≈6,000 lines of commerce code do not), not a fork that shares layers.

**Known gaps in the reference that the product must add.** No tenancy anywhere (zero `tenant_id` columns), no knowledge/RAG layer, no attachments, no HTML outbound, no charset handling on inbound, no Pub/Sub (1 poll/min/mailbox), no CSRF, no metrics/tracing, pricing table has one model, auto-mode bypassed the approve-time validator (fix: validator runs on every path).

## Product: how businesses use it

**Who it is for (v1).** Small businesses with a shared support inbox and repetitive questions: e-commerce stores, online services/SaaS, agencies, local service businesses. Typical volume 20–2,000 support emails/month. One "workspace" = one business; a workspace can connect several mailboxes/addresses and invite teammates.

**The owner's journey — onboarding is four server-tracked steps (profile → mailbox → knowledge → go live), resumable on any device; everything else lives in Settings.**
1. **Sign up** (email one-tap code, Google, or Microsoft) with the business name on the same screen → workspace created, user = owner.
2. **Profile** (~60 s): website URL, one-line description, tone (Friendly / Formal / Concise), timezone, the phone/URLs the agent may share. The derived guardrail summary appears ("Replies may link only to acme.com").
3. **Connect a mailbox**: "Connect Gmail" / "Connect Microsoft 365" with plain-words scope copy per provider → consent in the system browser → back in the app, the connection is **claimed** by the same signed-in user (this is a security requirement, see §Architecture). The step ends on **"Which addresses should the agent answer?"** — the primary address is listed *unchecked* with the copy "all mail to this address will be read by the agent and visible to your team"; add `support@`/`sales@` aliases here (verified by a one-time code the platform emails to the alias; if the alias cannot send as itself, choose "replies come from owner@acme.com" or set up Send-as — never blocked). Each address becomes an **agent** with the Support persona by default. We only ever fetch mail addressed to agent addresses in full.
4. **Knowledge** (~5 min, skippable with a warning): three cards — *Crawl acme.com* (prefilled, one tap, progress, page cap), *Paste FAQ/policies*, *Upload files* (PDF/DOCX/MD/TXT) — with a live "Ready: 3 sources · 212 chunks" counter, plus the **operating guidance** box with three example bullets ("we don't refund sale items", "sign as Team Acme", "never promise delivery dates").
5. **Go live**: every category at Review, threshold at Balanced, one sentence per category, then **"Send yourself a test email to support@acme.com"** — the box polls until the first draft appears (this is the trust moment and validates push), then the switch **Agent is ON**. Default policy: everything goes to Review except spam/auto-replies (dropped) and tripwire mail (escalated).

**After onboarding (Settings, not the funnel):** *Agents* (persona presets, custom persona text, signature, per-agent guidance, "Try it" sandbox per agent, up to 3 per domain); *AI* — Managed AI is the silent default; "Connect your own provider" (Anthropic, OpenAI, DeepSeek, or an OpenAI-compatible URL + key; the connection is probed and its capabilities shown; a plain notice says email content goes to that provider); *Autopilot* (per-agent × category Off / Review / Auto with the cold-start lock, threshold presets, safety words); *Team*, *Mailboxes*, *Billing*.

6. **Operate** from the phone or desktop: To review (drafts waiting + items that need a human, with a one-word reason), Auto-sending (countdown + Hold), Recent; Activity (what was auto-sent, with sources); Analytics (answered automatically %, median first response, confidence trend, top topics, **knowledge gaps** = questions the agent could not ground).
7. **Improve** with almost no effort: every approve/edit/reject teaches; the gaps report says what to upload next; suggested guidance rules appear after edits ("You changed 3 drafts to say returns take 10 business days — add this as a rule?"). Importing past conversations ("Remember this reply" on the owner's own replies) arrives in Phase 7, not at connect time.

**Does the business need to upload documents?** Not to start, but the agent is only as good as its grounding. Minimum viable knowledge = the profile paragraph + guidance + a crawled website. Documents and past conversations raise coverage and confidence. The product shows the coverage effect directly (sandbox + gaps report) rather than asking for uploads up front.

**Not in v1** (deliberate): commerce integrations (Shopify order lookup — the adapter seam exists), live chat / other channels / contact form, multi-language guidance UI (the model handles inbound languages; guidance is written in the owner's language), a customer-facing help center, SLA/assignment workflows, connect-time backfill of old mail, custom categories (8 seeded, labels editable), crawl include/exclude paths, per-agent knowledge scoping (knowledge is workspace-wide; personas and per-agent guidance cover the `sales@`/`info@` difference), overage packs (automatic overage or blocked only), biometric lock, offline cache.

## Learning loop (memory of past inquiries → rising confidence)

Robert's question: *"will it remember past inquiries so a similar question won't need review and confidence naturally goes up?"* — yes, by design, with three cooperating mechanisms:

1. **Resolved-case memory.** Every reply that a human **approved** (or edited then approved) becomes a *resolved case*: the customer's question (normalized, PII-stripped), the final sent answer, the category, the sources used, who approved it, and whether it was edited. Cases are embedded and stored next to the knowledge base. When a new inquiry arrives, the top matching cases are retrieved and given to the agent as "previously approved answers for similar questions" (trusted tier, below guidance). Auto-sent replies do **not** become cases until a human has sampled them (prevents self-reinforcement of a bad answer).
2. **Blockers vs. evidence** (computed in plain code; every term stored on the draft as `confidence_breakdown` and shown in the "Why" panel). *Blockers* are booleans that force Review or escalation regardless of any score: guardrail failure, tripwire, agent escalation flag, sender not DMARC-authenticated, memory conflict, attachments, unresolved questions, angry sentiment, language mismatch, thread longer than 6 messages, mailbox unhealthy, allowance exhausted. *Evidence* is what can make an Auto category send: `evidence = max(memory, grounding) × model`, where `memory` = banded cosine similarity to the best **active** resolved case the agent used (≥ 0.78 → 0.5, ≥ 0.84 → 0.8, ≥ 0.90 → 1.0, scaled by approvals up to 3), `grounding` = the best normalized retrieval score among validated citations, `model` = the agent's structured self-assessment. There is no "track record" term in the score: the owner graduating a category already encodes it. A fresh agent with no memory and modest grounding stays below every threshold; a question approved unchanged three times reaches memory 1.0 — this is "similar questions stop needing review". The chip shows "82% · would auto-send at 85%" so the gap is visible closing.
3. **Per-category graduation** (per agent). A category starts in Review with a **cold-start lock** (Auto cannot be enabled before 10 human decisions). The nightly rollup **suggests** Autopilot when the last 30 days show ≥ 20 decisions, ≥ 90% approved unchanged and no rejection in 14 days; the suggestion is computed as evidence — "would have auto-sent 17 of your last 20 unchanged approvals at Balanced" — and the threshold is set from that, so Autopilot delivers what it promises. One tap turns it on; owners can opt in to auto-graduation per agent. **Autopilot statistics include auto-sends**: an auto-send with no flag and no hold-then-edit within 7 days counts as confirmed, so the loop cannot stall once a category is mostly automatic. **Demotion is automatic**: two rejections in 7 days, two "should not have sent" flags, a hold followed by edit/reject, or an edit rate above 30% over at least 8 recent decisions sends the category back to Review with a visible reason.

**Feedback channels:** approve (positive case), edit (case with the corrected answer + an LLM-drafted *guidance suggestion* from the diff, accepted with one tap), reject-with-reason (re-draft loop; the reason becomes a case annotation and a guidance suggestion), escalate (excluded from memory), "should not have sent" on auto-sent replies (a strike on the answers used). **Retirement:** a case is superseded when a newer approved case contradicts it, when its source chunk changes or vanishes, or when the owner rejects a draft that relied on it; two strikes retire it; unused cases expire 365 days after the last human approval (no rolling renewal); superseded, retired and unsampled `candidate` cases are never retrieved. **Privacy:** question and answer text are structurally scrubbed before storage (greeting and signature dropped, addresses/phones/order-like digit runs/names masked), each case carries a per-org salted hash of the customer so an owner can delete everything learned from one customer.

## Architecture

Working codename **`aesa`** (from the repo name) is used for the URL scheme, the send-marker header and the DB roles; renaming later is a find-and-replace. Product name is an open item for Robert.

### Deployables (pnpm monorepo, Node 22, TypeScript, ESM, `tsx` runtime, runtime deps in `dependencies`)
1. **`apps/api`** — Fastify 5, stateless, N replicas. Better Auth (`/api/auth/*`, `organization` + `expo` plugins), tRPC (`/trpc`, Fastify adapter; end-to-end types into the app), mailbox OAuth (`/connect/:provider/start|callback`), provider + Stripe webhooks, one-click review pages (`/a/:draftId?t=`), presigned uploads, `/healthz`. **Never calls a model, never holds the KEK, never touches mail** beyond the OAuth code exchange. Sandbox runs and BYOK probes are enqueued as jobs, not run in-request.
2. **`apps/worker`** — pg-boss 10 workers + crons in the same Postgres. One image, partitioned by `WORKER_ROLES=sync,agent,send,knowledge,cron` so a knowledge burst cannot starve sends. The only process that decrypts OAuth/BYOK secrets and calls mail providers, LLMs, Voyage and Expo push.
3. **`apps/app`** — Expo universal app (iOS, Android, web; Expo Router; `web.output: 'server'` on EAS Hosting; fallback `static` + `generateStaticParams` stubs). tRPC + TanStack Query, `@better-auth/expo` client with `organizationClient()`, Expo push.
4. **Postgres 17 + pgvector** (one instance; direct pools; PgBouncer deferred until it is needed). Object storage for uploads (Cloudflare R2, S3 API). Resend for platform mail only (OTP, digests — never customer mail). Sentry for errors.

### Data flow: inbound → draft → decision → send
- **Inbound.** A push (Gmail Pub/Sub with OIDC token; Graph notification with per-connection `clientState`) is only a trigger: the api records `webhook_events`, resolves the connection through a `SECURITY DEFINER` resolver (the api never holds a bypass role), and enqueues `mailbox.sync {orgId, connectionId}` as a standard job with `singletonSeconds: 10` debounce. `mailbox.poll-sweep` (every 2 min) leases connections whose **sync is stale or push has expired/failed** (not merely quiet) plus a 30-minute safety poll; push is an accelerator, never a dependency. The worker runs the reference's cursor walk (ported `runIngest`/`runResync`) through the `MailboxClient` port: metadata-first fetch; **agent-address routing** — a message is fetched in full only when To/Cc/Delivered-To contains an `agents.address` on that connection (first match by `agents.priority`); DRAFT/TRASH skip; SENT-folder as the sole outbound signal; card-number scrub; `INSERT … ON CONFLICT DO NOTHING RETURNING id` gates every side effect; reopen rules and per-sender flood fold **apply only to DMARC-pass inbound**; the **platform tripwire** (word-boundary phrase match, baseline never removable + workspace additions) on every first-inserted inbound; guarded cursor advance. The **per-connection lease** in `mailbox_connections` is the real mutex (pg-boss `stately` is not relied on as one; Phase 0 pins the observed behaviour with a test).
- **Triage.** `ticket.triage` (role `triage` model, 20 s abort, usage row written before the call) assigns category, language, sentiment, spam/automated, escalation flags, `questions[]`. Precedence pinned from 6A: tripwire → spam/automated → escalate → triaged. Capped tickets are not stranded: the backstop re-enqueues after midnight and, when the cap is exhausted, moves them to `needs_owner/triage_cap` once per day.
- **Draft.** `ticket.draft` ports the 6B claim protocol (guarded CAS on `last_agent_run_at`, three watermarks, stuck-run recovery, `agent_failure_count`). Then a sequence of **short transactions — a `withOrg` transaction never spans network I/O**: (1) locked per-org gate + cap re-check + usage row, committed before any model call; (2) **pre-retrieval** in plain code (embed each triage question → knowledge chunks + resolved answers, exact cosine scan within the org); (3) one structured call through `LlmProvider` (prompt: platform rules → workspace profile → agent persona → knowledge block → guidance → thread, thread rendered as untrusted JSON lines); (4) plain-code **guardrails** on the body (one automatic redraft on hard failure), **evidence score**, and `decide()`; (5) one final transaction writes `drafts` + the ticket transition + `outbound_sends`/`notifications`.
- **Decision** (`packages/core/src/autonomy.ts`, pure, table-tested). Order: platform/workspace kill switch, agent disabled, subscription inactive → `review`; tripwire → `escalate` (cannot be turned off); agent `escalate` → `escalate`; agent `no_reply` → `no_action` (or `escalate: redraft_unfulfilled` when owner feedback was pending); guardrail failure → `escalate` (stored, editable, never sendable until the edited body passes); **sender not DMARC-authenticated → `review`**; category `off` → quiet `escalate`; category `review` → `review`; redraft → `review`; warnings → `review`; cold start (< 10 human decisions) → `review`; evidence below threshold → `review`; attachments / allowance exhausted / daily auto-send cap / mailbox unhealthy → `review`; else `send`.
- **Send.** `send.execute {sendId}` claims the ledger row, **re-reads every kill lever uncached inside the claim transaction** (platform killswitch, workspace `agent_enabled`/`kill_switch`, agent status, mailbox status, category mode) and holds the send if any is set; runs the validator a third time on the final body; staleness guard on `drafts.thread_snapshot_at` (NULL refuses); marker recovery scan first (`X-Aesa-Draft`; Graph additionally checks its persisted `createReply` draft id); an atomic `UPDATE … WHERE status='claimed' AND claim_expires_at > now()` immediately before `sendReply`; sends from the agent's real address with `In-Reply-To`/`References` (`buildReferences`, cap 20); reads back the real `rfc_message_id`; upserts the outbound message; conditional ticket flip; meters `ai_handled_conversations` once per ticket per month; enqueues `memory.capture`. Human approvals get `send_after = now + 15 s` so the undo toast is real; auto-sends get the agent's hold window (default 2 min).

### Where tenancy is enforced (three nets)
1. **Schema:** `org_id uuid NOT NULL` leads every tenant index/unique; RLS enabled + forced with `USING (org_id = NULLIF(current_setting('app.org_id', true), '')::uuid)`; runtime role `aesa_app` cannot bypass; migrations as `aesa_owner`; platform sweeps as `aesa_platform` with an explicit `USING (true)` policy scoped to that role and an audit line per `withPlatform()` call; the api never holds `aesa_platform` — its cross-org needs are fixed-signature `SECURITY DEFINER` functions (`resolve_mailbox_connection(provider, email)`, `resolve_subscription(id)`, `resolve_stripe_customer(id)`).
2. **Code:** `withOrg(db, orgId, fn: (tx: OrgTx) => …)` = transaction + `SET LOCAL app.org_id`; repositories accept only the branded `OrgTx`; ESLint bans the raw `Db` outside `packages/db` and a platform allowlist; `defineJob(name, zodSchema-with-orgId, handler)` injects an `AbortSignal` with deadline = `expireInSeconds − 30 s`; `enqueue()` refuses payloads without `orgId` and sets `singletonKey = ${orgId}:${entityId}`. `idle_in_transaction_session_timeout = 5 s` and a `statement_timeout` on the app role make a regression fail loudly.
3. **Runtime:** tRPC derives `orgId` from the session's active organization + membership; no procedure accepts an org id from input; cross-org ids 404 by construction; retrieval filters `org_id` in SQL and `assertSameOrg` re-checks before any text enters a prompt; object keys are `orgs/<orgId>/…`. CI isolation suite: two orgs, every procedure and job run as org A asserts zero rows from org B, including with a missing `SET LOCAL` and through a connection that previously ran one.

### Mailbox providers (`packages/mail`)
- **Port.** `MailboxProvider { authorizationUrl, exchangeCode, revoke, client(creds) }` and `MailboxClient { profile, subscribe/renew/unsubscribe, listChanges(cursor) (throws CursorExpiredError), listMessagesForResync, getThreadMessageIds, getMessage(id, {format:'metadata'|'full'}), sendReply (never retried inside the client), getDraftState, findSentByMarker }` over a `NormalizedMessage` (parsed lowercase addr-specs, all header occurrences, `authenticationResults`, attachments metadata, charset-honouring html-to-text body). `packages/mail/src/mock.ts` implements both (ports `createMockGmail` history semantics + pagination + multi-address routing + fault injection). The conformance suite runs one scenario file against the mock, recorded scrubbed fixtures, and (with `PROVIDER_CONTRACT=1`) real sandbox tenants.
- **Gmail.** Scopes `gmail.readonly` + `gmail.send` + `openid email` (least privilege; no labels, the product never mutates the mailbox; CASA applies either way). 3-legged OAuth with PKCE, `access_type=offline`. Push: `users.watch` → one platform Pub/Sub topic → `/webhooks/gmail` with OIDC; renew when < 36 h remain (7-day max). Cursor: `history.list` with BigInt-compared record ids; 404 → bounded resync (pre-captured `historyId`, `messages.list` per agent address `newer_than:30d`, per-page commits, re-walk known threads). Send: `messages.send` raw RFC 2822 with `threadId`; Gmail rewrites `Message-ID`, so the real id is read back after send. Webhook lookup by `PARTIAL UNIQUE (provider, email_address) WHERE status <> 'disabled'`. Rate limits: one GCP project for all tenants → per-connection bucket + process semaphore; 429/403-rate → `ProviderRateLimitError` honouring `Retry-After`; project-wide backoff row in `platform_state`. **While the consent screen is in Testing, external refresh tokens expire after 7 days**: health treats credential age as a scheduled reconnect (banner at day 5), and onboarding offers "Request Gmail early access" (operator adds the test user within a day).
- **Microsoft 365.** Delegated `offline_access User.Read Mail.ReadWrite Mail.Send` (`createReply` is the only way Graph sets threading headers; consent copy states plainly that Microsoft requires write access and that every Graph write is audited). PKCE, tenant `common`, `Prefer: IdType="ImmutableId"`. Admin consent (`AADSTS65001`) → "Send this to your admin" (api mails the admin-consent link; workspace shows "Waiting for your admin"). Push: `/subscriptions` on `/me/messages`, 3-day expiry renewed at < 36 h, validation handshake, `clientState` compared in constant time, lifecycle endpoint. Cursor: per-folder delta (inbox, sentitems, junkemail); `410`/`syncStateNotFound` → resync via `receivedDateTime ge <30d>`. Send: two-phase `createReply` → persist draft id → `PATCH` body/from/`x-aesa-draft` header → `send` → read back `internetMessageId`; re-entry checks `isDraft`. Microsoft publisher verification (MPN) starts in Phase 1.
- **Credentials.** Refresh under a short lease (`refresh_lock_until`), double-check after acquiring (another worker may have rotated the token; Microsoft rotates on every refresh), persist the new refresh token, mark `reauth_required` only when the failing refresh used the row's current `refresh_token_hash`. Disconnect = provider revoke + subscription delete + row delete + audit.
- **Connecting a mailbox safely (blocker fix).** `oauth_flows` row created by an authenticated tRPC call (`nonce_hash` unique, PKCE verifier encrypted, 10-minute expiry); the callback verifies and consumes the nonce, exchanges the code, and writes the connection as **`pending_claim`** (excluded from sync/subscribe/backfill and from the uniqueness rule); the app must call `mailboxes.claimConnection({flowId})` as the same user who started the flow before it becomes `connected`; on web the session cookie must also match. Unclaimed rows are revoked and deleted after 10 minutes. This closes the account-linking CSRF where an attacker attaches a victim's mailbox to their own workspace.
- **Agent addresses (major fixes).** Never pre-create an agent: the connect step ends on "Which addresses should the agent answer?" with the primary address **unchecked** and explicit copy ("all mail to this address will be read by the agent and visible to your team"). Adding an address to a connection someone else connected requires that person's one-tap confirmation (audited). An address that is not the connection's own is verified by an **inbound round-trip**: the platform emails a one-time code to the alias and the sync must ingest it on that connection with the alias in To/Delivered-To. If the alias is not a Gmail "Send mail as" alias, the owner chooses up front: replies come from the connection address (`agents.reply_from_address`) or they set up Send-as first — agent creation is never blocked.

### Agent runtime (`packages/agent` over `packages/llm`)
- **One structured call per draft** (`ChatRequest` with `output: DraftDecision`), pre-retrieved knowledge in the volatile block. Tool calling is a capability-gated second pass reserved for integrations (none in v1); the tool registry (`defineToolProvider({ key, requiredIntegration, sideEffects: false, build })`) exists so Shopify order lookup is additive later. A provider declaring side effects fails at boot.
- **Roles → models.** `triage` (managed `claude-haiku-4-5`), `draft` (managed `claude-opus-5`, `effort: medium` first attempt, `high` on redraft-with-reason), `guidance_suggest` (Haiku). Resolution: agent config → workspace default → plan default.
- **Prompt blocks with stability hints** (`static` → `agent` → `volatile`). Caching: breakpoint 1 = platform rules (cross-tenant, 1 h TTL, token count asserted above the model's minimum at boot); per-org/agent breakpoints only for orgs above ~12 drafts/hour (otherwise the write premium is never repaid — the merged plan's per-agent breakpoint was a finding). Cache-hit ratio metric per model.
- **`DraftDecision`** (zod, discriminated on `outcome`): `reply { categoryKey, body ≤ 4000 plain text, confidence 0..1, citedChunkIds, usedAnswerIds, memoryConflictIds, unresolvedQuestions, customerLanguage, rationale }` | `escalate { reason enum, rationale }` | `no_reply { reason enum, rationale }`. Cited ids are validated against what retrieval returned; a hallucinated citation zeroes grounding. A run that returns no parsable decision after the fallback ladder is an agent failure: retry once, then `needs_owner/agent_failed`.
- **Budgets.** Watchdog 240 s inside a 600 s job expiry; stop-loss $0.40 managed / 30k output tokens BYOK; per-ticket 3 runs/day (`1 + REDRAFT_MAX(2) ≤ 3`, asserted at boot); per-org concurrency 2; **per-org daily LLM USD cap** (trial $3, standard $60) and sandbox caps; **platform admission control** for managed runs via a `pg_try_advisory_lock` slot pool sized to our Anthropic tier (throttling is prevented, not reacted to); `maxRetries: 0` on the managed draft path with job-level retry; the platform daily cap throttles the top-spending orgs before pausing everyone. Every call is metered into `llm_calls` + `usage_counters` (see §LLM provider adapter).
- **Guardrails** (`packages/core/src/guardrails/validator.ts`, ported screens with a `WorkspacePolicy { allowedHostnames, allowedEmailDomains, allowedPhoneNumbers, maxChars, locale }`): (1) plain text ≤ max, no HTML openers, no invisible/bidi controls; (2) contact-channel screen; (3) URL/domain screen (exact host allowlist, bare-domain dot-boundary, userinfo tricks); (4) promised-action screen — a hard FAIL in v1 (no tool can back a promise); (5) secret-leak screen; (6) **trusted-text leak screen** — 10-word shingles of platform rules, guidance and persona text must not appear in a reply (prompt-injection exfiltration of the owner's internal stance); (7) unbacked numbers → WARNING; (8) language mismatch → WARNING; signature appended by code. Runs at three gates (draft, human approve on every surface, send) — one implementation, which closes the reference's auto-mode bypass.

### Queue and job model (`packages/queue` + `apps/worker`)
Jobs (all `defineJob`, payload carries `orgId`): `mailbox.sync`, `ticket.triage`, `ticket.draft`, `send.execute`, `knowledge.ingest`, `knowledge.crawl`, `knowledge.embed-batch`, `memory.capture`, `agent.sandbox`, `llm.probe`, `notify.dispatch`, `keys.rotate`. Crons (few, set-based, `fairSelect` round-robin over orgs, platform partial indexes for their predicates): `mailbox.poll-sweep` (2 min), `mailbox.renew-watch` (hourly), `ticket.backstop-sweep` (1 min: stuck runs, missed drafts, orphans, triage re-entry, held sends), `sweeps.daily` (draft expiry, memory retirement, retention, health rollup), `stats.rollup` (nightly), `notify.digest` (5 min), `billing.report-usage` (daily). Per-org fairness = per-org concurrency gate + per-org caps; no expression index on pg-boss internals.

### Notifications
Outbox table with dedupe + digest collapse (ported from `escalate.ts`). Push kinds: `draft_review` (actions **Review / Hold** — never Approve from the shade; approving requires the draft to have been rendered, `drafts.viewed_at`), `escalation`, `mailbox_reauth`, `graduation`, `demotion`, `digest`. No "Sent" push; `push_auto_sends` defaults off; auto-sent activity folds into the digest. Cap 30 pushes/org/day, overflow into the digest.

## Launch risks (known now)

- **Google restricted-scope verification.** `gmail.readonly`/`gmail.modify` are *restricted*; `gmail.send` is *sensitive*. Public launch needs OAuth app verification + CASA Tier 2 (self-serve labs ≈ $540–1,000; 4–12 weeks end-to-end; annual renewal). Until verified, the Google consent screen is limited to 100 test users. Mitigation: build the provider adapter so Microsoft 365 (no third-party audit; admin consent only) and a later forwarding-address adapter can launch independently of Google's timeline.
- **Deliverability of first-contact mail from new domains** (doge-buddy Finding B: Outlook.com silently drops). Sending from the business's own, already-warm address via their provider avoids this — it is the strongest argument for OAuth-send over our-own-domain sending.
- **PII + processors.** Customer mail flows to the model provider (Anthropic + Voyage under Managed AI; the customer's chosen provider under BYOK) and our Postgres. The privacy policy and DPA must say so, and the BYOK screen must state plainly that email content is sent to the provider the customer selected under that provider's terms. Scrub card numbers at ingest; never log bodies.
- **Quality variance across providers.** Confidence scoring and auto-graduation are calibrated on the managed default models. A weak BYOK/local model can produce confident-sounding bad drafts. Mitigations: capability probe on connect, per-model minimum bar before Autopilot is offered (graduation streak requirements scale with a model-quality tier), guardrails are provider-independent, and the sandbox makes quality visible before turn-on.
- **Custom endpoints are an SSRF surface.** BYOK base URLs must be https, resolve to public IPs, never follow redirects into private ranges, and run through an egress proxy with an allowlist option.
